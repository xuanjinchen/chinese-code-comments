## 背景

代码创建、修改、重构或修复完成后，需要形成稳定的注释检查习惯。该能力必须适用于前端、后端、C/C++、脚本、测试、SQL、基础设施配置等不同技术栈，并能根据当前任务已经使用或应当使用的领域 skill 理解改动意图，再生成准确、耐维护的注释。

单独依赖 skill 的隐式匹配无法保证每次代码改动都执行，因此采用“全局规则负责强制进入检查，专用 skill 负责检查和注释质量”的双层设计。

## 目标

- 创建通用用户级 skill：`chinese-code-comments`。
- 对所有项目生效，并在每次实际代码改动后强制执行注释检查。
- 在实现过程中及时记录关键意图，结束前再基于完整改动统一审查。
- 默认使用简体中文，同时支持用户指定英文、日文或其他语言。
- 默认只添加有维护价值的注释，同时支持用户指定逐行、代码块、方法、API 或其他注释基准。
- 按任务性质联动相关 skill，并复用已有分析结果。
- 保留准确的现有注释，不因全局规则无差别翻译或扩写代码。

## 非目标

- 不要求每次改动都必须产生新注释；完成检查后可以得出“不需要新增注释”的结论。
- 不默认翻译全部历史注释。
- 不通过注释掩盖不清晰的命名、过度复杂的实现或错误的代码结构。
- 不让注释修改改变程序逻辑、数据格式或外部行为。
- 第一版不使用 Hook 判断注释质量。Hook 可以执行机械检查，但不能可靠判断业务注释是否准确且必要。

## 总体结构

### 用户级 skill

将 skill 安装到用户级目录：

```text
<user-home>\.agents\skills\chinese-code-comments\
├── SKILL.md
└── agents\
    └── openai.yaml
```

`SKILL.md` 定义触发范围、优先级、两阶段工作流、按需 skill 联动、各类语言的注释策略和最终自检标准。

`agents/openai.yaml` 提供 UI 元数据，并保持 `allow_implicit_invocation: true`。隐式调用用于响应“补注释”“方法注释”“逐行注释”等直接或间接请求，但不承担每次代码改动必定触发的保证；普通只读代码解释不强制调用。

### 全局持久规则

在 `<user-home>\.codex\AGENTS.md` 中增加独立规则段，要求所有项目中的代码写入任务在结束前显式使用 `$chinese-code-comments`。

实施时必须保留该文件已有内容，只追加或更新本规则拥有的独立段落。即使当前文件为空，实施前也要重新读取，避免覆盖实施期间新增的用户内容。

当前安装器写入的规则语义如下：

```markdown
## Global Code Comment Policy

- 对产生代码写入的任务，必须在实现过程中记录有维护价值的关键意图，并在结束前显式使用 `$chinese-code-comments` 审查完整 diff；纯只读审查不强制执行两阶段流程。
- 普通逐行等价请求使用 `GROUPED`；只有正向、显式的全称约束使用 `STRICT`，否定式提及保持 `SCOPED`。
- 默认注释语言为简体中文；语言优先级为：用户明确指定、项目就近规范、简体中文。
- 默认只注释业务意图、约束、边界、异常、并发、资源管理、兼容性和非直观实现。用户明确指定注释范围、粒度或基准时，以用户要求为准。
- 保留准确的现有注释及其语言。只有注释因代码改动而失真、错误或冲突时才更新。
- 即使无需新增注释，也必须在最终回复中报告已完成注释审查。
```

项目中更接近代码的 `AGENTS.md` 或 `AGENTS.override.md` 可以细化具体模块的注释规范；用户在当前任务中的明确要求仍具有最高优先级。

## 触发边界

全局规则适用于产生代码写入的任务，包括：

- 新建功能、组件、服务、库或脚本。
- 修改、重构、迁移或优化代码。
- 修复缺陷、安全问题、测试失败或性能问题。
- 新增或修改测试、SQL、迁移、基础设施代码以及支持注释的配置文件。

仅阅读、解释、讨论或审查而未修改文件时，不强制执行结束前 diff 注释流程；用户直接要求评估或编写注释时仍可隐式或显式触发 skill。

默认排除生成代码、第三方依赖、压缩文件、锁文件以及不支持注释的严格数据格式，例如标准 JSON。除非用户明确要求且目标格式允许，否则不向这些文件写入注释。

## 优先级规则

### 注释语言

按以下顺序确定本次新增或更新注释的语言：

1. 用户在当前任务中明确指定的语言。
2. 当前代码所在目录最近的项目规范或一致的现有注释约定。
3. 简体中文。

保留准确的英文、日文及其他语言注释。只有它们已失真、错误或与本次改动冲突时才更新，并使用本次确定的目标语言。

### 注释基准与粒度

按以下顺序确定注释方式：

1. 用户明确指定的范围、粒度、格式和关注点。
2. 项目就近规范和语言惯用文档格式。
3. 默认高价值维护注释。

默认高价值维护注释重点解释：

- 业务意图和业务不变量。
- 输入输出约束及边界条件。
- 异常、降级、重试和恢复策略。
- 并发、异步、事务、幂等和一致性约束。
- 资源所有权、生命周期、清理和释放。
- 兼容性、协议、数据迁移和历史约束。
- 无法仅从代码表面准确理解的实现原因与风险。

用户可以指定逐行注释、代码块注释、方法或函数注释、类注释、API 文档注释、参数、返回值、异常或其他自定义基准。

当用户只说“逐行注释”时，默认把连续且语义一致的简单语句合并为一条注释。当用户明确说“每行都要”“一行一注”或表达等价要求时，才为每条可执行语句分别注释。严格逐行模式仍须使用目标语言的合法注释语法，并保持代码可编译、可解析和可格式化。

## 两阶段工作流

### 实现阶段

1. 读取任务要求、项目规范和相关代码上下文。
2. 确定目标语言与注释粒度。
3. 在实现复杂业务规则、边界保护、并发控制、异常恢复、资源清理或兼容逻辑时，同步记录关键意图。
4. 不为变量赋值、普通循环、显而易见的函数调用等代码逐句复述，除非用户明确要求对应粒度。
5. 不猜测无法从需求、代码、测试、文档或领域 skill 结论验证的业务事实。

### 结束前完整审查

1. 获取本次完整改动。Git 项目优先检查 diff 和未跟踪文件；非 Git 项目使用本次实际触及的文件集合。
2. 结合周边实现、测试和文档复核改动意图，不能只阅读新增行。
3. 查找缺失、重复、显而易见、错误或已经失真的注释。
4. 按语言和粒度优先级新增、更新或删除注释，仅修改与本次改动相关的范围。
5. 确认注释没有改变逻辑、破坏语法、泄露秘密或承诺未经验证的行为。
6. 运行与改动风险相称的格式化、语法检查或既定测试；若任务已经运行相关验证，不无理由重复执行。
7. 在最终回复中简要说明注释审查结果；即使没有新增注释，也应说明已完成检查且未发现需要补充的位置。

## 按需联动其他 skill

`chinese-code-comments` 的唯一职责是生成、更新和审查代码注释。辅助 skill 仍按各自匹配条件联动，其结论只作为理解注释意图的输入，不构成本项目的额外能力；不得为了增加注释而强制运行不适用的辅助 skill，并优先复用当前任务已经得到的结论：

- Bug、失败测试或异常行为：使用 `systematic-debugging` 的根因、触发条件和防回归结论。
- 功能完成、高风险修改或合并前检查：使用 `requesting-code-review` 识别的风险、约束和回归面。
- 公共 API、复杂业务、架构或维护说明：使用 `technical-writer` 提炼领域术语、契约和读者需要的上下文。
- 前端、React、移动端、架构、测试等任务：仅在相应 skill 的正常触发条件满足时使用对应领域 skill。

联动 skill 的结论用于理解代码和决定注释内容，不直接复制冗长分析到源码。若辅助 skill 已在当前任务使用，不重复执行同一分析。

## 注释质量标准

新增或更新的注释必须满足：

- 正确：与当前代码、测试和已确认需求一致。
- 必要：能提供代码本身无法清楚表达的信息，或满足用户指定粒度。
- 耐久：描述稳定意图和约束，避免记录短期实现过程或聊天上下文。
- 简洁：使用最短但足以防止误解的表达。
- 就近：放在相关声明、分支、代码块或 API 附近。
- 惯用：采用目标语言和项目已有的行注释、块注释、docstring、Javadoc、TSDoc 等格式。
- 可维护：代码行为变化时同步更新，失真时删除或重写。

以下内容默认不应添加：

- 对代码字面行为的简单翻译。
- 无依据的业务解释或未来计划。
- 与实现重复且更容易失真的长篇说明。
- 用注释替代清晰命名或必要重构。
- 密钥、令牌、隐私数据或内部敏感信息。

## 异常与冲突处理

- 用户要求与全局默认冲突时，遵循用户当前任务中的明确要求。
- 项目规范与默认简体中文冲突时，遵循项目就近规范。
- 项目规范与用户明确要求冲突时，遵循用户要求，并在可能影响团队一致性时于最终回复说明。
- 目标文件不支持注释时，不写入非法内容；改为在相邻文档、代码或最终回复中说明，具体方式由任务范围决定。
- 无法确定业务意图时，先从需求、测试、文档和相关 skill 结果取证。仍无法确认且错误注释风险较高时，不在源码中猜测，并在最终回复指出缺失信息。
- 如果完整审查表明代码已经自解释且没有维护上下文需要记录，保持代码不变并报告审查完成。

## 验证方案

### 结构校验

- 使用 `skill-creator` 的 `quick_validate.py` 校验名称、YAML frontmatter 和目录结构。
- 校验 `agents/openai.yaml` 与 `SKILL.md` 的名称、描述和默认提示一致。
- 确认隐式调用未被关闭。

### 触发用例

- 未提注释的 Java 后端功能修改：由全局规则显式要求结束前使用 skill。
- 未提注释的 React 组件修改：执行完整 diff 审查，只对状态同步、交互边界等非直观内容注释。
- C 语言缓冲区缺陷修复：结合调试结论说明边界与资源释放。
- C++ 所有权转移修复：在 `std::move` 边界前完成访问，并说明转移后的失效约束。
- SQL 部分唯一索引：通过可执行迁移验证并发唯一性不变量。
- Terraform 滚动发布：验证可用副本和额外容量约束。
- 用户要求“给方法写日文注释”：使用日文和方法级文档格式。
- 用户要求“逐行中文注释”：按连续语义分组。
- 用户要求“每一行都写英文注释”：严格逐条注释，并保持语法有效。
- 现有英文注释仍准确：保留，不翻译。
- 现有英文注释因逻辑变化失真：按本次目标语言更新。

### 反向与边界用例

- 代码逻辑简单且自解释：执行检查但不强行新增注释。
- 只修改标准 JSON：不插入非法注释。
- 只做代码解释且不改文件：不强制运行 diff 审查。
- 生成代码或依赖文件发生变化：默认不添加注释。
- 已经使用相关领域 skill：复用结论，不重复运行。

### 全局规则验证

- 从任意项目启动新的 Codex 会话，检查其加载的用户级指令包含全局注释规则。
- 执行一个不包含“注释”字样的小型代码修改任务，确认 Agent 在结束前显式使用 `$chinese-code-comments`。
- 检查最终回复能够区分“补充了注释”和“已审查但无需补充注释”。

## 实施边界

实施阶段只创建并安装 `chinese-code-comments`、更新全局 `AGENTS.md` 的独立规则段，并执行上述验证。不引入 Hook、不创建插件、不修改无关 skill，也不改动任何业务项目代码。

本规格已经用户书面确认并完成实施。实现额外提供可捕获失败回滚的安装和卸载、结构化行为评测，以及不提注释的真实 Git 写入烟雾测试；这些增强不改变“不使用 Hook、不创建插件”的边界。多文件更新无法在进程被强制终止或系统重启时提供跨文件原子保证，因此文档不把它描述为崩溃安全事务。

最终动态验收覆盖 19 个结构化行为案例。无提示写入 smoke 还从 JSONL 轨迹验证 `chinese-code-comments` 和缺陷场景所需的 `systematic-debugging` 均在编辑前读取，并要求最终 `git diff` 事件实际输出目标文件 patch；其他辅助 skill 仍只在各自正常触发条件满足时按需联动。
